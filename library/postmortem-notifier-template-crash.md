# Postmortem: notifier queue stalled by a template error

Last updated: 2026-07-28  
Owner: Tom (notifier)  
Participants: Tom (notifier owner), Yuki (notifier engineer), Sara (platform engineer, on-call primary), Kenji Sato (platform lead), Hana (support lead)

---

## 1. Summary

On Tuesday, 2026-07-28, `notifier` stopped processing all outbound emails and SMS messages across the primary region (`ap-northeast`) for 48 minutes. The outage occurred because a newly registered business profile included an unhandled non-standard character sequence in its display name. When a customer completed a booking with this business, `api` enqueued an appointment confirmation message. 

Upon dequeuing this message, `notifier`'s worker process crashed during template string interpolation prior to handing the rendered message off to our delivery vendors. Because worker processes fetch jobs without an immediate dead-letter disposition on crash, each of the three regional worker nodes in `ap-northeast` repeatedly picked up the exact same payload at the head of the queue, crashed instantly, and entered a restart cycle. 

With all worker nodes cycling through crashes, zero messages were delivered between 14:12 JST and 15:00 JST. The backlog reached a peak depth of 2,750 waiting messages. Yuki (notifier engineer) isolated the crash trace in the logs, identified the poison payload, and manually moved the bad message aside into an isolated debug topic. Once the blocked item was cleared, the remaining backlog drained completely within 15 minutes. 

No customer data was exposed or permanently lost, and no money moved incorrectly. However, appointment confirmations, receipts, and SMS sign-in codes were delayed by up to an hour during a peak afternoon period.

---

## 2. Impact

- **Duration:** 48 minutes of full message delivery interruption (14:12 JST to 15:00 JST). Total recovery time including backlog drainage was 63 minutes (14:12 JST to 15:15 JST).
- **Service delivery:**
  - Outbound email and SMS delivery rate dropped to 0 messages per minute across `ap-northeast`.
  - Queue depth accumulated to a peak of 2,750 waiting messages on the `notifier` primary regional queue.
  - An estimated 1,940 customers experienced delayed booking confirmations, reschedule notifications, or email receipts.
  - Approximately 180 users attempting SMS-based sign-in experienced code delivery timeouts and had to switch to email sign-in or wait for resolution.
- **Customer harm:**
  - Hana (support) reported 34 support inquiries regarding missing booking confirmation emails and delayed one-time verification passwords.
  - Zero appointment records were lost; all 2,750 queued jobs were delivered successfully once workers resumed, with the exception of the single parked message.
- **Data & Financial integrity:**
  - No data was leaked, corrupted, or visible across tenant boundaries.
  - No payment or refund operations were affected directly, though receipts generated by `payments` were held in the queue.
- **Severity assessment:**
  - Treated as a P1 incident under Section 2 of the handbook: a core customer communication pipeline was entirely stalled during business hours, leaving customers unable to receive their booking confirmations or authentication codes.

## 4. Root Cause Analysis

### 4.1 The Template Interpolation Crash
`notifier` templates are evaluated inside a worker loop prior to dispatch. When `api` publishes an event (e.g., `booking.created`), it sends a serialized JSON payload containing the business name, customer reference, slot time, and pricing information. 

At 14:08 JST, a salon operator updated their profile name. The name included an uncommon Unicode sequence consisting of an unassigned code point combined with right-to-left override and control bytes. When the confirmation template engine rendered the greeting block, an uncaught encoding error was raised within the formatting filter. Because this specific exception was not captured in the worker's application-level `try/catch` block, it escalated directly to the OS process supervisor, terminating the node instance immediately.

### 4.2 The Poison Pill Queue Cycle
`notifier` uses an explicit acknowledgment pattern with the AWS message broker:
1. Worker retrieves a message batch.
2. Worker processes and renders the template.
3. Worker sends payload to SendGrid (email) or Twilio (SMS).
4. Worker acknowledges and deletes the message from the queue.

If the worker crashes abruptly at step 2, the message remains unacknowledged. After the message visibility timeout elapsed (which was configured to 0 seconds on process disconnection), the broker released the message back to the front of the queue. Because our regional worker footprint consists of three worker nodes reading from this single queue, the first node crashed, the second immediately picked it up and crashed, and the third did the same. This produced an unbroken loop where no subsequent messages could be evaluated.

## 5. What Went Well

- **Alerting accuracy:** The rule `notifier-queue-stalled` fired as expected at the 15-minute mark of complete message starvation, providing clear visibility that delivery was at zero despite queued traffic.
- **Handbook adherence:** Sara correctly prioritized `read logs` over attempting an unjustified rollback of a 4-day-old release, rapidly diagnosing that the issue stemmed from application crashes rather than an external provider outage.
- **Escalation speed:** Once it was clear that worker code was crashing deterministically on production payloads requiring queue data manipulation, the owner (Tom) was paged promptly without wasting time on futile node restarts.
- **Rapid drain:** Once Yuki cleared the single blocking message, `notifier` cleared all 2,750 backlogged messages in 15 minutes without exceeding SendGrid or Twilio rate limits.

---

## 6. What Went Badly

- **Lack of automated isolation (dead-lettering):** A single bad payload was able to bring down the entire notification pipeline for an entire region. The absence of a retry limit before quarantine turned an isolated template bug into a total regional outage.
- **Late status page posting:** Although the incident thread was opened within minutes of the alert, the public status page was updated at 14:47 JST—35 minutes after the failure began, and slightly past the 20-minute handbook target from time of confirmed customer impact.
- **Support visibility:** Support agents had to field calls regarding missing SMS login codes before an internal broadcast went out, forcing support to triage tickets blindly between 14:25 and 14:35 JST.

---

## 7. Where We Got Lucky

- **Provider capacity:** The queue drained at peak burst speed (over 200 messages/minute) without running into SendGrid account rate caps or Twilio carrier dispatch bottlenecks, which would have prolonged the delay further.
- **Business hours timing:** The incident occurred in the middle of a weekday afternoon when Yuki, Tom, and Sara were immediately available at their desks. Had this crash occurred during the scheduled 02:00–04:00 JST reminder queuing batch, thousands more messages would have backed up before manual intervention took place.

## 8. Corrective Actions

The primary architectural flaw identified in this incident is that a malformed message was allowed to block the queue indefinitely. The following action items were agreed upon during the postmortem review:

| Action Item | Owner | Target Date | Status |
|---|---|---|---|
| **Implement automatic poison-pill parking:** Configure `notifier` queue consumers and the broker so that any message that crashes a worker twice is automatically routed to a `parked` (dead-letter) queue without human intervention. | Yuki | 2026-07-28 | **Done** |
| **Harden template rendering filter:** Wrap the Jinja2 template interpolation block in a defensive sanitization handler that escapes or strips invalid control characters and logs a warning instead of raising an unhandled exception. | Tom | 2026-07-31 | In progress |
| **Add input validation in `api`:** Update `api` profile name validators to reject unprintable Unicode control characters and invalid direction overrides at submission time. | Daniel | 2026-08-05 | In progress |
| **Review visibility timeout configuration:** Review worker crash retry semantics to ensure failed workers back off with a non-zero visibility timeout, preventing hot crash loops. | Sara | 2026-08-07 | Planned |
| **Status page notification drill:** Run a refresher for on-call engineers and incident commanders on updating `status.sorrel.app` within the 20-minute window on silent P1 failures. | Kenji Sato | 2026-08-12 | Planned |

## 9. Appendix: Technical Reference & Metrics

### 9.1 Queue Recovery Profile
- **Pre-incident baseline:** 15–40 messages queue depth, oldest message age < 15 seconds.
- **14:12 JST:** Queue depth starts climbing at ~55 messages/min. Delivered rate drops to 0.
- **15:00 JST:** Queue depth peaks at 2,750 messages. Message parking executed.
- **15:15 JST:** Queue depth returns to 32 messages. Delivered rate normalizes to 40 messages/min.

### 9.2 Parking Implementation Note
As of 2026-07-28 evening, Yuki deployed the automated parking fix to `notifier` worker nodes in `ap-northeast`, `us-east`, and `eu-west`. The broker redrive policy now tracks delivery attempts per message ID. If a message receives an execution attempt count of $\ge 2$ without an explicit ACK or graceful retry exception, the broker shunts the envelope directly to `sorrel-notifier-parked-[region]`, emits alert `notifier-message-parked`, and proceeds to the next item on the primary queue. This guarantees that a corrupted or malformed template payload will never stall downstream customer traffic again.
