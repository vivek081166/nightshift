Postmortem: api date search slow after a migration
dropped an index

Incident date 2024-07-09 (Tuesday, afternoon JST)

Severity SEV-2

Service api

Incident commander Mei

Author Ravi

Status Final, reviewed 2024-07-11
Summary

api deploy d-4471 carried migration 0193, which dropped the old index on bookings (business_id,
starts_at) before its replacement had finished building. Every date search on a booking page then read
the bookings table without an index, the primary database ran hot, and date search was slow for 69
minutes. Rolling back the code did not help, because a rollback does not bring back a dropped index.
Date search recovered when the new index finished building at 15:19.

Impact

e Customers: date search on booking pages took 2 to 6 seconds between 14:12 and 15:21 JST, and
some searches timed out. Support received 212 tickets.

e Bookings made in that window were about 35 % lower than in the same hour the week before.

e Money and data: no payments affected, nothing lost or exposed.

What happened

Incident declared (SEV-2). Mei takes incident commander. Support reports
customers saying the booking page spins when they pick a date.

Tom rolls api back to the previous deploy, d-4466. The code goes back, but
the dropped index does not come back with it.

Latency has not recovered seven minutes after the rollback. Tom pages Ravi,
because the database now needs the owner's decision.

Ravi joins and finds the background index build at 41 %, with about 35
minutes left at its current speed.

Ravi decides not to recreate the old index by hand, because two index builds
would compete for the same disk. The team waits for the build.

Support has 190 tickets so far. Mei posts a notice on status.sorrel.app that
date search is slow and that bookings still go through.

The new index finishes building. p95 for the availability endpoint falls to 240
ms within two minutes.

Ravi deploys d-4471 again, so the code matches the new index.

Mei closes the incident after 15 minutes of normal latency and updates the
status page.

What went badly

e The migration dropped the old index before the new one existed. Rolling back the code could not
undo that, and nobody on the incident knew it until the rollback had failed.

e The api-wide p95 alert hid how slow the availability endpoint alone had become.
